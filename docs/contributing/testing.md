# Tests

- Unit tests sit next to the code (`foo.ts` → `foo.test.ts`) and run in Node. Architecture tests live in `tests/architecture/`, and tests for the JavaScript in `scripts/` in `tests/scripts/` (Vitest runs only `src/` and `tests/`). A test that needs adapters and the UI together, which may not import each other, lives in `src/integration/`: the run panel's findings for real template runs, for example.
- **UI tests** start with `// @vitest-environment jsdom`, render with [Testing Library](https://testing-library.com/docs/react-testing-library/intro/), and call `cleanup` in `afterEach`. Give components use cases through `UseCasesProvider`: `fakeUseCases()` rejects every call you don't override, and `inMemoryUseCases()` runs the real project use cases over in-memory adapters (both in `src/ui/app/testing/`).
- **Use jsdom only for a test that needs the browser:** one that renders, or reads `document`, `window`, or `localStorage`. jsdom adds 3 to 5 s of startup to each file in a full run. Everything else runs in Node, where the setup file skips loading Testing Library.
- **Run each whole-template simulation once: one file per run.** A whole-template run takes 0.8 s (steady day, Template A) to 7.6 s (long rush, Template B), and the files that run them are about 40% of the suite's CPU time. The files in `src/adapters/templates/runs/` are named for the run (`template-b-long-rush-seed-42.test.ts`) and are the only ones that start a simulation. Each calls `useRun` (`testing/use-run.ts`), which runs it in a `beforeAll` with `RUN_TIMEOUT_MS`, and gives the run to the suites of every topic that reads it. A suite is a `*.suite.ts` module of `describe` blocks that takes a run getter, and ESLint treats it like a test file for length and parameter counts. A new check on a run goes in a suite, or in a new one that the run's file calls; it doesn't start its own simulation. Vitest starts the files that took longest last time first, but it counts only test and hook time, so a file that does its work while collecting looks fast and starts last: run in `beforeAll`, not in a `describe` body. A file's runs are serial, so the slowest file sets how long a full run takes: give each long rush its own file, and let the short runs share one across seeds. Two kinds of test keep their own runs: the run panel's (`src/integration/`), which needs jsdom and the real run adapter, and the CLI's report snapshots (`src/adapters/cli/`), which pin the command's output.
- **Where is the test for…?** By topic, in the suites; by run, in `runs/`. The scenario's lesson (the `it` names) is in `scenarios/*.suite.ts`; the expected findings, in `findings/findings-cases.ts` and `findings/backlog-at-end.suite.ts`; the rejection reasons, in `testing/describe-rejection-reasons.ts`, with each run's expected causes in its file; the sums that must reconcile, in `cli/report-reconciles.suite.ts` and `templates/run-analysis-reconciles.suite.ts`. Search for the `it` name, as the findings catalog's Observed claims do.
- The coding standards apply to tests too. ESLint skips the length and parameter checks there, because a `describe` block groups many tests; keep each test itself within the rule of 30, and split a long scenario into named steps.
- Tests should be able to fail. When you write or change one, break the code it covers and watch it go red at least once. Then say how you broke it in a comment above the test, so a reviewer can check it without rerunning it and a later reader knows what the test guards:
  ```ts
  // Fails if the queue drops messages that are still in flight when the run ends.
  it("counts in-flight messages in the totals", () => {
  ```
  Write one comment per `it` or `it.each`. For a change to a shared suite (`checkComponentContract` and the other contract checkers), put it on the check you changed. A regression test's comment names the bug it guards against: the change that turns it red is the bug coming back.
- Use the seed, not luck. Anything random runs from a fixed seed. Scenario tests that assert a template's lesson check several seeds (`src/adapters/templates/scenarios/`, run by `runs/`) with loose thresholds, so they pin the lesson rather than one run's numbers.
- **Contract suites** check that an implementation keeps the promises of its interface. Every component type must pass `checkComponentContract`, every `ProjectRepository` adapter must pass `checkProjectRepositoryContract`, and every `SimulationRunner` must pass `checkSimulationRunnerContract`, each with an empty list of violations.
- **Outputs must reconcile.** Totals in metrics and reports add up: started = succeeded + failed + in progress, and so on. Show work that's still in progress rather than dropping it, and test the remainders (see `src/adapters/cli/report-reconciles.suite.ts`). Add a check when you add a column or a counter. To find a workflow or component in a snapshot, use `workflowIn` and `componentIn` (`src/domain/metrics/testing/`) instead of chains of `?.`.
- Latencies carry floating-point drift (`49.000000000000014`): compare them with `toBeCloseTo`. Percentiles are bucket upper bounds, up to 5% high ([metrics guide](../architecture/metrics.md)).
- Model changes come with before/after numbers from `npm run simulate` in the PR description.

## Gotchas

- **Put the path before `--update`.** Vitest's `-u` takes an optional value, so `npx vitest run -u <path>` treats the path as that value, runs the whole suite, and rewrites every snapshot. Write `npx vitest run <path> --update`.
- **Slow full runs.** Vitest starts one worker per thread minus one, so a 16-thread laptop runs 15. That oversubscribes the CPU: tests slow down 6–10× (a 2 s test takes 18 s) and UI tests, or slow ones such as `layer-rules`, which runs ESLint, time out at random. They pass alone. `vite.config.ts` therefore caps local runs at 50% of the threads; CI (`CI` set) keeps Vitest's default, which suits its 4 vCPUs. Don't raise the test timeouts: that hides the contention. `isolate: false` and `pool: "threads"` don't help either, because worker startup isn't the bottleneck. If the chart test in `OpenedProject.test.tsx` times out, open a new issue rather than reopening [#27](https://github.com/alanbickel/wind-tunnel/issues/27).
- **CSS in tests is empty.** Vitest turns every CSS import into an empty string, `?raw` included, unless the file matches `test.css.include` in `vite.config.ts`. The contrast test reads `tokens.css` that way; a test that needs another stylesheet's text adds it there.
- **Measuring the test suite.** The percentages in Vitest's summary are shares of time summed across workers, not of the wall time. For a breakdown by file, write a throwaway reporter whose `onTestRunEnd` prints each module's `diagnostic()`, which gives its environment, setup, collect, and test times. Leave `isolate` on, even though Vitest suggests turning it off: files would share module state, and `Diagram`'s loading test fails whenever another file in the same worker has already loaded React Flow.
