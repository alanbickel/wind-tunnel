# Getting Started

The starting point for maintainers. It takes you from a fresh clone to your first change in about an hour of reading. To find a particular document later, use the map in the [root README](../README.md#documentation).

## 1. Set up

Follow [Setup in the contributing guide](../CONTRIBUTING.md#setup), then run `npm run check`. If it passes, your machine matches CI.

To see the engine work before reading about it, run a template headlessly:

```sh
npm run simulate -- --template template-a
```

The [headless runner guide](architecture/headless-runner.md) explains how to read the report.

## 2. Read in this order

Each step builds on the one before. Keep the glossary open throughout.

1. [Glossary](glossary.md): every domain term in a line or two, and how the runtime nouns nest. (~4 min)
2. [Architecture overview](architecture/architecture-overview.md): the layers, the dependency rule, and where code goes. (~10 min)
3. [The domain model](architecture/domain-model.md): what a project holds, workflows as call trees, and how documents are loaded and validated. (~7 min)
4. [How the simulation engine works](architecture/simulation-engine.md): the event queue, the behavior primitives, and a request's journey through calls, timeouts, and retries. (~14 min)
5. [Component definitions](architecture/component-definitions.md): how a service type plugs into the engine through effects, and the contract every type must pass. (~11 min)
6. [How metrics work](architecture/metrics.md): ticks, per-second snapshots, run totals, and latency histograms. (~9 min)
7. [The application layer and persistence](architecture/application-layer.md): use cases, ports and their adapters, and a project traced end to end through IndexedDB. (~10 min)
8. [The user interface](architecture/user-interface.md): how components reach the use cases, and a run traced from the Run button to the charts. (~10 min)

Skip the [MVP design](design/mvp-design.md) for now. It's the detailed reference behind the guides; read the section you need when you need it. The same goes for the [ADRs](adr/adr-overview.md): skim their titles, and read one in full when you touch the area it covers.

## 3. Make your first change

1. Find the current task in the [implementation plan](implementation-plan.md): the first unchecked task in the first milestone not marked ✅.
2. Find where the code goes in the overview's ["Where does my code go?"](architecture/architecture-overview.md#where-does-my-code-go) table, and read the guide it names.
3. Read the [contributing guide](../CONTRIBUTING.md) before writing code. The coding standards are strict, and lint fails on a violation. (~12 min)
4. Run `npm run check` before you commit.

## Learn by running traces

The guides quote timelines generated by tests in [`src/domain/traces/`](../src/domain/traces/), [`src/adapters/traces/`](../src/adapters/traces/), and [`src/ui/traces/`](../src/ui/traces/). To understand a piece better, add a scenario to the trace test for its guide and read the output. That is often quicker than stepping through a debugger.
